# RFC 6638 Scheduling Foundation — Design

> Solo todo #56. Authored and self-approved under delegated autonomy (the maintainer
> asked for an autonomous implementation ending in an open PR).

## Goal

Lay the foundation for CalDAV scheduling (RFC 6638) so that calendar clients see
scheduling inbox/outbox collections, principals advertise their calendar-user
address, and the server can store scheduling (iTip) objects. This is the gateway
todo that unblocks auto-schedule (#57), free/busy (#58), iMIP (#59), and
availability (#60).

## What sabre gives us for free

Research (see PR description) established that `Sabre\CalDAV\Schedule\Plugin` plus
the existing CalDAV + DAVACL plugins do almost all the protocol work once two
conditions hold:

1. The calendar backend implements `Sabre\CalDAV\Backend\SchedulingSupport`.
2. Each principal exposes `{http://sabredav.org/ns}email-address`.

Specifically:

- `CalendarHome` automatically adds virtual `Schedule\Inbox` (`inbox`) and
  `Schedule\Outbox` (`outbox`) nodes when the backend `instanceof SchedulingSupport`.
  The Inbox proxies to the backend's four scheduling methods; the Outbox is a
  static POST endpoint that needs nothing from the backend.
- `calendar-user-address-set` is already produced by the **CalDAV plugin** from the
  principal URL plus the principal's email — our `PrincipalBackend` already exposes
  `{http://sabredav.org/ns}email-address` (from `DavOwner::getDavPrincipalEmail()`),
  so CUAS works as soon as a principal is queried.
- `schedule-inbox-URL`, `schedule-outbox-URL`, and `schedule-default-calendar-URL`
  are produced by the **Schedule plugin** once it is registered. They resolve from
  `getCalendarHomeForPrincipal('principals/<id>') → calendars/<id>`, which matches
  our existing layout. They report 404 (not error) when unavailable.
- `getCalendarObjectByUID()` already has a working default in `AbstractBackend`, so
  the plugin's delivery path does not fatal.

## Scope of this PR (foundation only)

1. **Storage**: new `dav_scheduling_objects` table + `DavSchedulingObject` model for
   inbox iTip messages, keyed per owner.
2. **Backend**: `CalendarBackend implements SchedulingSupport` — the four methods
   (`getSchedulingObject`, `getSchedulingObjects`, `createSchedulingObject`,
   `deleteSchedulingObject`) CRUD against the new table, resolving `principalUri`
   via the existing `ResolvesPrincipalUri` concern.
3. **Server**: register `Sabre\CalDAV\Schedule\Plugin` in `ServerFactory` (after the
   CalDAV and ACL plugins it depends on). `IMipPlugin` is **not** registered, so no
   email leaves the server.
4. **Tests**: HTTP feature tests (`Rfc6638/SchedulingTest`) for CUAS + schedule URLs
   on a principal, inbox/outbox presence in the calendar-home, and inbox object
   listing; a backend test (`Sabre/SchedulingBackendTest`) for the four CRUD methods;
   `SchemaTest` gains the new table; the `CaldavServerTesterTest` snapshot is
   regenerated by running the tester locally.
5. **Docs**: README + CHANGELOG updated.

## Storage model

`dav_scheduling_objects`:

| column | type | notes |
|---|---|---|
| id | bigint pk | |
| user_id | foreignId → owner table, cascadeOnDelete | the inbox owner (principal) |
| uri | string | unique basename within the inbox |
| calendar_data | longText | verbatim iTip iCalendar payload |
| etag | string | `sha1(calendar_data)` |
| size | unsignedInteger | `strlen(calendar_data)` |
| last_modified_at | timestamp | |
| timestamps | | |

`unique(['user_id', 'uri'])`, matching `dav_calendars`.

`DavSchedulingObject` is a plain Eloquent model (fillable `user_id`, `uri`,
`calendar_data`, `etag`, `size`, `last_modified_at`). etag/size are derived in the
backend's `createSchedulingObject`. These objects are opaque transient messages —
**no** `CalendarObjectData` cast, **no** `TracksDavResource` change-recording, and
the inbox is not wired into the sync-token system. They are deliberately minimal.

## Backend row shape

`getSchedulingObject` / `getSchedulingObjects` return rows mirroring `objectRow`:
`['id', 'uri', 'lastmodified' => unix ts, 'etag' => '"…"', 'size', 'calendardata']`
(`calendardata` may be omitted from the list form but we include it — it is cheap).

## Explicitly out of scope (deferred)

- **`schedule-tag` / `Schedule-Tag` / `If-Schedule-Tag-Match`** — sabre/dav implements
  none of this; it is independent custom work (a separate change tag on calendar
  objects + precondition handling). Deferred to a follow-up todo. The caldav-tester
  `scheduling.schedule-tag` check will reflect whatever support results from the
  foundation, captured honestly in the snapshot.
- **Auto-schedule verification (#57), free/busy (#58), iMIP (#59)** — registering the
  plugin activates sabre's local-delivery and free-busy-POST handlers as a side
  effect, but proving/verifying those workflows (and the caldav-tester gradings) is
  their own todos. This PR only guarantees the foundation pieces and that existing
  behavior (plain event/contact writes) is unchanged.

## Risk & verification

- Registering the Schedule plugin must not regress existing protocol tests (plain
  events carry no ORGANIZER/ATTENDEE, so the broker produces no messages). Verified
  by the full suite.
- The `CaldavServerTesterTest` snapshot **runs in CI** (the workflow installs
  `caldav-server-tester`). It will change once `scheduling` is no longer fully
  unsupported, so it is regenerated by running the tester locally
  (`uv`/`caldav-server-tester` are available) and the assertions updated to the real
  output — not guessed.
- Raw iCalendar round-trip is preserved (scheduling objects store payloads verbatim).
